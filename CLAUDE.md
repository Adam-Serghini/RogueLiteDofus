# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

**V0 + V1 are implemented** (TS + Vite, vanilla DOM). The original V0/V1 spec files have been removed from the repo — the implementation itself is now the reference for what exists. The only remaining doc is:

- `GDD-roguelite-dofus.md` — the full game vision. Background only; consult it for *why* a system exists, never to widen scope beyond the current tranche.
- `PLAN-CONTENU.md` — the long-term content roadmap (5 tranches, rarity, boss signatures).

Both docs are in French; the game's domain vocabulary (PA, sorts, esquive, élément de frappe, Dofus…) is French and is kept as-is in code identifiers and data.

- **Generic engine fields introduced for the Iop rework** (2026-08-07, `types.ts`/`combat.ts`, `iop-moteur.test.ts`): `Spell.ratioLigne` (Pugilat) hits the main target at full power and the REST of its row at a fraction — distinct from `zoneLigne`, which hits the whole row at full power; resolved in `ciblesDegats` (a new branch mirroring the `zoneLigne` one) and in the damage multiplier. `Spell.bonusParRelanceCeTour` (Pugilat) and `Spell.bonusParLancerCombat` (Colère de Iop) are two escalation multipliers, one scoped to the current turn and one to the whole combat — **both share the exact same off-by-one trap**: `lancersCeTour[sort.id]`/`lancersCombat[sort.id]` are incremented BEFORE damage resolution runs, so on the FIRST cast the counter already reads 1, not 0. The multiplier is therefore `1 + valeur × Math.max(0, compteur − 1)`, never `1 + valeur × compteur` — the latter would silently double-count the first cast, and a test that only exercises a single cast would not catch it (both instances are covered by a three-cast test asserting ×1.0 → ×1.2 → ×1.4 and ×1.0 → ×1.5 → ×2.0 respectively). `Combatant.lancersCombat` (keyed `sortId`, like `lancersCeTour`) is the engine's first PER-COMBAT cast counter — unlike `lancersCeTour`, it is never reset by `reinitialiserLancersTour` and survives every turn change of the same fight; it still can't leak between fights since combatants are rebuilt from `RunState` per encounter. `Spell.bouclierPortee: { portee: "soi" | "rangee_lanceur" | "rangee_avant"; pct: number; tours?: number }` (Endurance, Vertu) is a shield-on-a-row-with-a-duration triplet that **already existed**, buried inside the Ecaflip's Roulette faces (`FaceRoulette.portee`/`.bouclierPct`/`.duree`) — extracted into a shared helper, `appliquerBouclierPortee` (plus a small `ciblesPortee` helper for the beneficiary selection), so the Roulette faces and the two new Iop spells now call the SAME resolution instead of duplicating it (`src/ecaflip.test.ts`/`src/feca-moteur.test.ts` stayed untouched and green as the proof the extraction changed no behaviour — NOT `ecaflip-moteur.test.ts`, which happens to carry no Roulette face using `bouclierPct` and would have stayed green even if the mechanic had been deleted outright). Resolved from BOTH of `lancerSort`'s paths exactly once per cast, never once per target (Endurance is a damage spell, Vertu a buff — same two-call-site pattern as `effetRangeeAlliee` on the Féca): a shield without `tours` is PERMANENT and uncapped, which is why both Iop carriers declare one; `aFriction` still blocks it, and `boucliersTemporaires` still claws back only `min(montant, bouclier restant)` on expiry. `Spell.paImmediat` (Précipitation) is the first field to credit `paActuels` — the CURRENT turn's pool — directly and immediately, as opposed to `paGain`/`paProchainTour`, which both only ever credit `paBonusNextTurn` (the NEXT turn). Verified rather than assumed: `runCombat`'s turn loop already re-reads `acteur.paActuels` off the live reference on every iteration of its inner `while`, so no engine change was needed for the extra PA to be spendable within the same turn (a dedicated integration test proves it by casting Précipitation then a spell the starting PA pool could not have afforded).

Zénith (4 PA, `ennemi_ligne`, `zoneLigne`, `bonusParPADispo: 0.07` — reuses the Cra's Flèche Punitive field verbatim, no new engine: at 6 PA it counts 6, i.e. +42%, because the turn loop debits `paActuels` BEFORE calling `lancerSort`, so "PA available" reconstitutes as `paActuels + sort.coutPA`), Pugilat (2 PA, `maxParCibleParTour: 1`, `ratioLigne: 0.5`, `bonusParRelanceCeTour: 0.2` — full damage to the target, half to the rest of its row, +20% per relance THIS turn, escalation applying to the splash too per Adam's call), Endurance (2 PA, `maxParTour: 2`, `bouclierPortee: { portee: "soi", pct: 0.08, tours: 1 }` — hits and shields the caster for 1 turn, two casts in the same turn STACK rather than refresh), Colère de Iop (5 PA, cd 2, `bonusParLancerCombat: 0.5` — a heavy single-target hit escalating +50% per PREVIOUS cast for the rest of the fight, uncapped by design, the cooldown and fight length being the only brakes), Précipitation (0 PA, `maxParTour: 1`, cd 3, `paImmediat: 3` — **the first 0-PA spell in the game**, see below), Vertu (3 PA, cd 3, `bouclierPortee: { portee: "rangee_lanceur", pct: 0.15, tours: 2 }` — shields the caster's own row, caster included). **The Précipitation → Zénith combo is the kit's designed peak**: Précipitation is free and grants 3 PA for the current turn only (lost if unspent, unlike `paGain`/`paProchainTour`); chained into Zénith at a base 6 PA, the counter reads 9 before payment, i.e. +63% — paid for by 3 turns of cooldown. **Précipitation's 0 PA cost interacts with the automatic end-of-turn** (`aUneActionPossible` in `ui/combat.ts` tests `paActuels >= s.coutPA && ciblesValides(...).length > 0`): the PA-check half of that predicate is trivially true at 0 PA remaining for a 0-cost spell, so the turn will NOT auto-end while Précipitation is still available — this is the CORRECT behaviour (the player can still cast it to refill for the turn); once cast, `maxParTour: 1` makes `ciblesValides` return an empty list for it and normal auto-end-of-turn resumes, since `ciblesValides` applies `maxParTour`/cooldowns before even looking at target type. **This is why the content validator's minimum-cost guard was rewritten rather than just loosened**: it used to reject any `coutPA < 1` outright; a 0-PA spell now instead MUST declare `maxParTour` or `cooldownTours` (`scripts/content-validate.mjs`). **Deliberately NOT `maxParCibleParTour`**: a per-TARGET limit would still let `iaAgressif` recast the spell on a DIFFERENT target every decision of the same turn, PA never decreasing — it caps who gets hit twice, not how many times the spell fires in a turn, so it does nothing to stop the loop this guard exists to prevent. Without `maxParTour`/`cooldownTours`, a free damage spell handed to a monster would be reselected every single decision of the same turn and fire dozens of times with no validation or test ever catching it. **Éléments, robustness note**: the pair change makes the Iop **strictly more fragile without hitting harder** — it trades terre's passive vitality (`Math.floor(force/5)`, ≈29 PV at the reference curve) and feu's `multOffensif` (up to +20% final damage) for air's crit (chance+damage, capping at roughly +16% average damage, slightly below feu's +20%) and eau's prospection, which is **dead in combat**. All of the kit's extra damage therefore comes from its spells, none from its elements — consistent with "more damage, fewer survival tools," but the robustness gap this opens is sharper than a mere loss of defensive spells would suggest.
- **Taunt leaves the player's camp for good** (2026-08-07, Iop rework): the retired Duel was the LAST hero spell carrying `Spell.provoqueTours` — a deliberate call, made in full knowledge that `CLAUDE.md` had flagged this rework as the moment to decide. No playable class can force enemy targeting anymore; only the Féca's l'Égide still protects an ally, and by interception, not by taunt. This is the fourth mechanic to leave heroes after friction, dispel, and transmissible poison — with one difference: those three still live on monsters, while taunt survives only on an invocation belonging to a **disabled** class (the Sadida's Poupée, via `Combatant.provoque`, still read by `ciblesValides`). **The cleanup went deeper than the spell itself**: removing `Spell.provoqueTours`/`Spell.contre`/`Spell.siCibleMeurt`/`Spell.passeTourSiSurvie` (all four orphaned — no remaining carrier in `sorts.json` or code) left THREE `Combatant` fields with no poser left alive — `Combatant.provoqueTours`, `Combatant.provoquePoseCeTour`, and `Combatant.passeProchainTour` — each of which had exactly ONE poser in the whole game, the very spell field just removed. These were retired too, same jurisprudence as `nbCibles`/`bonusDe`/`elementImpose`. **The one to remember**: `Combatant.provoque` (the flag `ciblesValides` actually reads) is untouched and still lives, permanently, on the Poupée — but its entire DURATION bookkeeping is gone, including the only line in the engine that could ever turn a taunt back off (`decrementerEffets`'s `provoqueTours` countdown, which zeroed `provoque` at expiry). **Consequence for whoever revives a taunt one day, hero or monster**: there is no dial to turn, no field to reconnect — a TIME-LIMITED taunt requires rebuilding this bookkeeping (a duration field, a "just posed this turn, skip one decrement" guard like `provoquePoseCeTour` had, and the countdown itself) from scratch. The riposte posture (`contre`, `Spell.contre`) lost its own last hero carrier the same way but keeps every mechanism alive: `sommeEffet(cible, "contre")` is still posed by the Wobots' `effetLanceur` (Terrier du Wa Wabbit, toile 17) and by the Sabre Shodanwa's `riposteAvant` — two channels entirely independent of the removed `Spell.contre` block, so no bookkeeping was lost there.
- **Structural gap surfaced, not fixed, by this rework**: none of the five new fields (`ratioLigne`, `bonusParRelanceCeTour`, `bonusParLancerCombat`, `bouclierPortee`, `paImmediat`) is rendered by the spell tooltip (`sortTooltipHtml`, `ui/composants.ts`), which only knows how to format name, cost, roll, description, target, and cooldown. The five mechanics reach the player through the spell's free-text description alone. Content tests now freeze those descriptions, which rules out the immediate risk of silent drift, but the gap is structural and applies equally to every already-reworked class (Ecaflip, Féca, Eniripsa…) carrying similarly untooltipped fields — flagged here as a possible future chantier, not a defect of this one.
- **The balancing harness was NOT run for this rework, at Adam's explicit request** (unlike the Féca rework, which used the Iop-less reference team as a deliberate control and confirmed zero measurable side effect — see *Rework Féca* below). Note for later: the Iop, unlike the Féca, **is** in the sim's reference team (Iop/air·eau · Cra/air · Eniripsa/feu · Ecaflip/eau since this rework), so the next `npm run sim` run WILL move its numbers — partly for a reason that has nothing to do with the kit's actual strength: `controllerIA` only ever plays `type: "degats"` spells, highest-cost first, so it will **never** cast Précipitation or Vertu (both `type: "buff"`), and will always prefer Colère de Iop and Zénith over Pugilat regardless of the escalation math. The sim will therefore structurally under-read this kit, the same way it already under-reads the Kwakwa's mue, the Meulou's per-turn cancels, and the Domaine Ancestral's web.
- **Recruitment**: start with 2, recruit/heal at tavernes, team of 4 max.
- **Equipment** (`ITEMS` in `data.ts`, re-exported from `src/content/items.json`): **4 slots** — `arme`/`coiffe`/`cape`/`anneau` (amulette/ceinture/bottes were removed to cut micro-management and leave room for item rarity). All items are **toile/rarity items** with FIXED stats per tier (`Item.tiers`, no rolls) — the legacy panoplie system (`PANOPLIES`, `BUTIN_ZONE`, `Item.rolls`, rolled-at-drop stat ranges, per-set stat bonuses) has been fully purged; see Item rarity (toiles) below for the live system. **Panoplies (light, reintroduced 2026-07-24)**: the 4 set pieces of each zone carry `Item.panoplie` (the display name — 12 sets × 4 pieces in t1); wearing all 4 pieces of one set grants **+1 PA** (`PANOPLIE_BONUS_PA`/`comptePanoplies` in run.ts, folded into `bonusEquipement().paBonus`; shown under the equip slots in the inventory). Elite/boss items belong to NO set — equipping one breaks the bonus (deliberate tradeoff). No 2-piece tier, no per-set stat bonuses. **Per-run** loot — `RunState.inventaire` + `PersoState.equipement` hold `ItemInstance` objects, lost on death; **Prospection** boosts drop rate. Equipment stats/PV/resistances fold into the combatant via `bonusEquipement`/`pvMaxPerso` in `run.ts`.

### Archimonstres & Dofus Ocre

**Le Bestiaire est en onglets par tranche** (2026-08-04, `showBestiaire` réécrit autour d'un `draw()`) : avec 24 zones la liste d'un seul bloc était interminable. Seules les tranches POURVUES de zones ont un onglet (t3-t5 vides → une mention discrète en pied), chaque onglet porte son avancement (`compteTranche`), et les classes CSS vivent dans `src/style.css` (`.tranche-onglets`, `.tranche-onglet`, `.tranche-niveaux`).

**Archimonstres ERRANTS — les six Piou (2026-08-05)** : première mécanique de capture qui ne passe **par aucune zone**. Les six Piou (Rouge/Vert/Bleu/Jaune/Rose/Violet) ont chacun un archi réel chez Metamob et n'appartiennent à aucun donjon des 24 zones — donc à aucun pool, donc à aucune rencontre : six archis inatteignables. Ils surgissent maintenant **en plus d'un pack de combat NORMAL de Tranche 1**, via `ERRANTS` (`data.ts`, indexé par tranche) et `appliquerErrants` (`run.ts`), appelée dans `main.ts` **après** `appliquerArchimonstres` et annoncée dans le titre du combat (`· ⭐ <nom>`) comme les modificateurs d'élite. **Ils arrivent DÉJÀ mutés en archi**, et c'est structurel, pas cosmétique : soumis au tirage habituel, capturer un Piou précis vaudrait P(apparition) × 1/6 × 2,4 %, soit ~0,04 % par combat même à 10 % d'apparition — la mécanique ne remplirait pas son objet. D'où l'extraction de **`muterEnArchi`** (déplacement de code depuis `appliquerArchimonstres`, aucun changement de comportement, avec une garde anti-double-mutation). **Le taux est UNE valeur, `ERRANTS.t1.chance` = 1 %**, délibérément **sans levier** — ni philtres d'Otomai, ni Prospection, ni Ascension : le seul archi sur lequel le joueur n'a aucune prise. ≈0,7 Piou par run de t1 (~72 combats normaux), soit ~20 runs pour les six ; **c'est reconnu comme peu et la valeur est FAITE pour monter** (1,5 % évoqué), donc **aucun test ne code 0,01 en dur** — ils lisent la constante et vérifient un ordre de grandeur. **Jamais en élite ni en donjon** (`type === "combat"` seulement) : ces salles sont équilibrées, et une salle de boss tendue pourrait devenir infaisable. **Volontairement faibles** : 12 PV, 4 PA, dominante 14, un seul sort (`coup_de_bec`) → 24 PV / 21 en archi, soit la bande d'Incarnam (15-22 PV) — le calibrage vise **le premier combat d'une run, pas la moyenne**, et un test chiffre la fourchette pour que personne ne les gonfle un jour. Les quatre couleurs canoniques portent un élément (Rouge feu, Vert terre, Bleu eau, Jaune air) ; **Rose et Violet sont hors carré donc sans pic élémentaire** (même traitement que la Larve Champêtre). Côté Bestiaire, un bloc **« Rencontres fortuites »** clôt l'onglet t1 et **les deux compteurs (total global et avancement de tranche) les comptent** — sinon le dénominateur mentirait. **Les deux garde-fous globaux de `zones.test.ts` ont été REFORMULÉS, pas assouplis** : « toute espèce est placée en zone **OU déclarée errante** », plus un test qui vérifie ce qui rend un errant réellement atteignable (taux > 0, archi, sort) — en faire des exceptions nommées aurait affaibli des gardes qui venaient de trouver un vrai bug (le Tofu Maléfique). **`npm run sim` ne les verra jamais** (il appelle `fabriquerEnnemis` sans traverser `main.ts`), donc aucun chiffre d'équilibrage ne bouge. `src/combat.ts` inchangé.

Any enemy can rarely spawn as a boosted "Archi" variant (`ARCHI` in `data.ts` — base rate 0.8%; the **Otomai node is the philtre event**: each visit permanently adds +`ARCHI.philtre` (0.4%) for the rest of the run via `RunState.philtres`/`chanceArchi(run)`, 🧪 badge on the map — the old restat screen `showOtomai` was removed. **Capped at `ARCHI.philtresMax` = 4 philtres** (2026-08-02): measured on 400 simulated runs, a player who *detours* toward every Otomai collected ~11 per run and finished at 5.2% per enemy — 6.5× the base rate, ~8 archi spawns/run, filling the bestiary in a handful of runs while the Ocre tiers are meant as a long-term goal. Capped, both play styles land at 2.4% (~5 archis/run) and the detour stops paying. **Known consequence to revisit**: even a passive player collects ~6.5 philtres, so *everyone* hits the cap around mid-run and the later Otomai nodes give nothing — if that reads as filler in playtest, lower the node's `GEN_CARTE.poids` (8 today) rather than raising the cap); defeating it captures the species once (persistent `Meta.archis`), tracked in a per-zone **Bestiaire** (`showBestiaire` — lists **every** species of each zone incl. boss/miniboss, with capture state on the archi-capable ones; 54 capturable species across the 16 zones (34 in t1, 20 in t2); the Kankreblath and Larves-donjon species genuinely have no archi on Metamob — archis attach to the base/outdoor variants). Zone rosters follow the **real DofusDB dungeon compositions** (`api.dofusdb.fr/dungeons/{id}` → `monsters[]` + `bosses[]`) — check there before inventing species. The **Dofus Ocre** is no longer a boss drop — it unlocks in tiers every 50 captures (`OCRE_PALIERS`), granting escalating team passives (PA + damage) via `bonusEquipe(meta)` (combines Dofus + Ocre). Not reachable with the current ~16 monsters by design (framework for a bigger bestiary, ~286).

### Kamas, HDV & Forgemagie

- **Kamas**: per-run currency in `RunState.kamas`, lost on death; earned on victories via `gainKamas` — node type × toile, ±15% variance — and by selling at the HDV. Shown on the map sidebar and in the recap. Constants in `KAMAS` in data.ts.
- **Hôtel de vente**: `hdv` NodeType, tile `cases/hdv.png`, excluded from Incarnam. Stock = `genererStockHDV`, PREMIUM shop: current-toile items only at épique/légendaire, next-toile items from rare up (~40% of slots when it exists; commun/rare local gear comes from fights). Buy price `KAMAS.prix` by rarity × toile, resale 50%.
- **Forgemagie**: `forgemagie` NodeType, weight 6 in `GEN_CARTE.poids`, excluded from Incarnam, tile `cases/forgemagie.png`. The Forgemage upgrades ANY owned instance (inventory or equipped — mutation in place via `forgerInstance`, so the reference stays valid) to its NEXT defined rarity tier; cost = HDV price of the TARGET tier × `KAMAS.forgeCoef` (0.6). The **Forgemage téméraire** costs ×0.3 but fails 30% of the time (kamas lost, item intact — `KAMAS.forgeTemeraire`). Max-tier items (and any instance without a next defined tier) are not forgeable (`rareteSuivante`); `showForgemagie` previews the target tier's stats and records forged tiers in the Armurerie collection.

## What the game is

A turn-based tactical roguelite in the Dofus universe, played in the browser. The single loop V0 must validate: **tactical combat + a permanent relic (Dofus) that survives death and makes the next run easier**. Everything is judged against one question — *is the combat fun?*

## Tech stack

- **TypeScript + Vite**, vanilla — **no React, no Canvas**. UI is plain DOM. The point is to test *feel*, not visuals.
- **Data-driven**: classes, spells, monsters, encounters, map-generation params and tuning constants live in `src/data.ts`, not hardcoded in logic.
- **Vitest** for the pure modules (`combat`, `progression`, `carte`) — validated headlessly, independent of the DOM.
- Persistence: the `Meta` object (owned Dofus, captured `archis`, `runs`/`victoires` counters, `succes`, `collection`) survives runs, saved to `localStorage` (key `rld_meta_v0`, with rétro-compat defaults in `chargerMeta`). Player *settings* (end-turn key, auto-end-turn, default formation row per class) persist separately under `rld_settings_v0` (`src/config.ts`). The **run in progress** persists under `rld_run_v0` (`sauverRunEnCours`/`chargerRunEnCours`/`effacerRunEnCours` in `run.ts`): saved after every resolved board node and at zone transitions; a combat in progress is NOT saved (refresh = redo the node); cleared on wipe/victory/abandon (abandon counts as a failed run); the start screen offers Reprendre/Abandonner when a save exists. Levels/points/HP live in `RunState` and reset on death.
- Deploy: pushing `main` publishes to GitHub Pages via `.github/workflows/deploy.yml` (`GITHUB_ACTIONS=true` sets Vite `base` to `/RogueLiteDofus/`).

## Code map & architecture

The hard line in this codebase: **`combat.ts` is pure** (no DOM, no `localStorage`) and **`src/ui/` is presentation only** (no game rules). Everything is wired in `main.ts`. Keep new logic on the correct side of that line — it's why the engine is unit-testable.

- `src/types.ts` — the data model (interfaces straight from the spec): combat types, `Progression`, equipment types (`Item` with fixed-stat `tiers`, the rolled-rarity `ItemInstance`, `EquipSlot`), and map types (`MapNode`, `GameMap`).
- `src/data.ts` — all content & tuning: `SORTS` (**12 classes**: Iop, Cra, Eniripsa, Sadida, Sram, Feca, Ecaflip, Ouginak, Roublard, Xélor, Éliotrope, Forgelance + monsters), `CLASSES`, `MONSTRES` (bestiary across 24 zones), `DOFUS` (31-relic catalogue), `COMBATS` (per-zone encounters; boss encounters = **boss + miniboss**), **`ZONES`** (24 zones, flat) + **`TRANCHES`** (`TrancheDef`: no `active` flag — `niveaux: [start, cap]` is the source of truth, `t1 [1,50]`, `t2 [50,100]`, `t3 [100,150]`, `t4 [150,199]`, `t5 [200,200]`; t1 = the 12 zone ids in play order — Incarnam → Champs d'Astrub → Tainéla → Tofus → Akadémie des Gobs → Kankreblath → Maison Fantôme → Scarafeuilles → Forgerons → Larves → Grotte Hesque → Nid du Kwakwa, ordered by official dungeon level; t2 = 12 zones (complète) (`clos_des_blops`, `cale_de_l_arche`, `gelaxieme_dimension`, `laboratoire_brumen`, `terrier_wa_wabbit`, `pitons_rocheux`, `bateau_du_chouque`, `antre_dragon_cochon`, `repaire_kharnozor`, `taniere_meulou`, `domaine_ancestral`, `arbre_de_moon`), t3-t5 still `zones: []` — see Multi-tranches below; event dungeons Nowel/Halouine/Pwak are reserved and must never enter tranche zone lists; each zone has `pools = {normales, elite, boss}` typed `ZonePools` — **`boss` is a `string[]`** (since the Clos des Blops shipped multi-boss rooms), not a single id: the donjon node draws its final room via `pick(rng, pools.boss)`, so a zone can have several boss encounters). Resolvers `trancheDe(trancheId)` (t1 fallback for unknown/legacy ids), `localiserZone(zoneId)` (which tranche + index a zone belongs to), `offsetToile(trancheId)` (toiles consumed by PRECEDING tranches — toile numbering is **continuous** across tranches: t1 = toiles 1-12, t2 = 13-24, so loot/HDV pricing/kamas/XP scaling never resets). `XP_PAR_TYPE`, `XP_PAR_TOILE`, `xpEffective(xpBase, toile, trancheId)` (applies the toile multiplier then the tranche's optional `xpMult`), `TAVERNE_PCT`, `GEN_CARTE` (the board is a **Pokelike diamond lattice**: alternating staggered rows of 2 — columns ±0.5 — and 3 — columns −1/0/+1 — with edges = exact diagonals |Δcol| = 0.5; row count 10-12 rounded to even so the last 2-row converges on the single donjon). Each class/monster has an optional `img` (path under `public/assets/…`). Sprites/icons and base stats/resistances are pulled from **DofusDB** (`api.dofusdb.fr` JSON + `/img/monsters/{gfxId}.png` CDN — keyed by **gfxId**, not monster id; the website itself is a JS SPA and not fetchable). **Archimonstre names** (`archiNom`) come from **Metamob**, which is more complete than DofusDB for archis — see the `archimonstre-source-metamob` memory for how to read its bundled static catalog without an API key.
- `src/content/*.json` — **source de vérité du contenu** (sorts, classes, monstres, combats, zones_pools, items, butin_toiles), sérialisation canonique (`scripts/canonical.mjs` : clés triées, indent 2) pour des diffs git lisibles. `src/data.ts` importe ces JSON et les ré-exporte typés (plus de `src/items_gen.ts`, supprimé). Garde permanente `src/content.test.ts` : le contenu doit passer `scripts/content-validate.mjs` (3 passes) à chaque run de tests. **`npm run content:import` est la porte du GAME DESIGNER**, pas la seule voie d'écriture : sa passe 3 interdit délibérément d'ajouter une zone (`"zone ajoutée interdite"`) ou de créer un sort (`"création de sort interdite"`) et ne tolère que des changements numériques sur les sorts existants. Un ajout **structurel** (zone, sort, classe — le cas du Clos des Blops) se fait côté développeur par script jetable réécrivant le JSON avec `stringifyCanonique` (`scripts/canonical.mjs`), sous la garde des passes 1-2 de `src/content.test.ts` (schéma, cohérence référentielle) rejouées à chaque `npm test`.

Two key seams keep things testable and decoupled:
1. **Combatants are rebuilt per fight** from `RunState` — final stats and `pvMax` are computed in `run.ts` and baked into the `Combatant`, so `combat.ts` stays ignorant of levels/points. HP persists via `PersoState.pvActuels` (written back by `synchroniserPV`), not by keeping the combatant object around.
2. **The async controller pattern**: `runCombat` `await`s the active camp's controller, so the same loop runs headless (IA vs IA in tests) or interactively (promise resolved by a DOM click) with no branching in the engine.

### Core combat rules that are easy to get wrong

- **Élément de frappe (AUTOMATIQUE per-cible, 2026-08-06 rework)**: there is no stored strike element anymore — no `elementChoisi`, no manual choice, no ronds to click. Element ↔ stat is still `terre→force`, `feu→intelligence`, `air→agilité`, `eau→chance`. At the moment of EACH hit, the hot path `meilleurElement(lanceur, cible, base, jetTire)` (`combat.ts`, private, called from `degatsAvec` with the ALREADY-ROLLED damage roll) picks — among the caster's **candidate elements** — the one the CURRENT target resists the least, using the real damage-resistance formula shared with the pipeline (never a second RNG draw; ties broken by candidate order). `elementContre(lanceur, cible, sort)` is the exported DISPLAY wrapper (enemy card highlight, tooltip callers) — same formula, but on an AVERAGE roll rather than the real one, since no roll exists yet outside an actual hit; the two can diverge only when a buff/gear desyncs a combatant's two elemental stats. Candidates (`elementsCandidats`): a hero's fixed **pair** (`Classe.elements`), a monster's **top-2 stats** (`elementsForts` falls back to the two highest of force/intelligence/agilité/chance when `c.elements` is unset), or **all 4** if the combatant carries `elementLibre` (Kwakwaffe — unchanged, still the one item that widens the pool instead of narrowing it to a click). `elementDeFrappe(c)` is the cible-less variant (best candidate by raw stat) — used by `multSoin` and by any display outside targeting. Consequence: **every hit can use a different element**, even against the same enemy across two spells if a debuff shifted its resistances mid-fight; `ResultatDegats.element` carries the element actually used so the log and the UI never repeat a stale choice.
  - **Readability**: an enemy's card, while a player-camp actor is acting, highlights (in the 2×2 resistance grid) the element `elementContre` would pick against it right now — an *information*, computed live, never cached on the combatant. The combat log names the element used on every hit and riposte (`elNomCourt(r.element)`), so nothing is silently decided.
  - **Monster invariant**: since the target-aware pick reads whichever of a monster's stats is highest, a monster is expected to have **exactly one** meaningful elemental stat — a second one above 60% of the dominant would make its own "weak element" fuzzy and undermine the elemental puzzle zones. Enforced by `src/monstres.test.ts` (`SEUIL = 0.6`), with **10 named, pre-existing exceptions** kept until arbitrated as balancing (not fixed by this rework): `boufton_blanc`, `directeur_grunob`, `gardienne_champetre`, `kardorim`, the four `kwakere_de_*` (they share one identical stat block — their elemental identity is purely cosmetic today), `kwakwa`, `sergent_chafer`. A second test in the same file asserts every listed exception is genuinely over the threshold, so the list can't silently grow stale.
- **Grid & line rule (SYMMETRIC, 4×2 per camp)**: `position` is a grid cell **0-7** — cells **0-3 = ligne avant**, 4-7 = arrière (`estAvant(c) = position < 4`, `combat.ts`). `ennemi_ligne` spells hit only the target camp's front-row living; if the front row is empty, the back becomes exposed (`ligneFront`). Applies to **both** camps. `ennemi_tous` ignores it; rebound (Flèche perçante) hops by ascending position; taunt (`provoque`) overrides. Placement is free: all-front, all-back, mono-tank, etc. Players placed via **formation** (`config.formation` = `{classeId: cell}` → `PersoState.position`), edited from the board grid (`showFormation`); enemies placed by encounter `position` cells in `data.ts` (up to 8). Combat cards are vertical, grouped into front/back rows per camp.
  - **`lancerSort` n'applique lui-même AUCUN filtre de ligne** (découvert pendant le rework du Féca, 2026-08-07) : toute la règle de ligne — `ennemi_ligne` vs `ennemi_tous`, `tetanise`, `ignoreLigne` — vit exclusivement dans `ciblesValides`, consultée par l'IA et l'UI **avant** l'appel à `lancerSort`, jamais par `lancerSort` lui-même. Conséquence pratique pour les tests : un test qui veut prouver quelque chose sur le **ciblage** (« ce sort peut/ne peut pas atteindre telle case ») doit passer par `ciblesValides`, jamais par `lancerSort` seul — celui-ci résout le sort sur N'IMPORTE QUELLE cible qu'on lui passe, valide ou non. Piège réel rencontré sur ce chantier : un premier test de Bulle (`ennemi_tous`, censé atteindre la rangée arrière même rangée avant vivante) appelait directement `lancerSort` avec la cible arrière comme seule assertion — un sabotage du contenu (`cible: "ennemi_tous"` → `"ennemi_ligne"`) laissait le test PASSER À L'IDENTIQUE, preuve qu'il ne prouvait rien sur le ciblage. Corrigé en assertant d'abord `ciblesValides(...).toContain(cible)`, seule assertion réellement discriminante.
- **Damage pipeline** (order matters, see `degatsCible` in `combat.ts`): esquive check (Agilité, capped) → roll (or max if `maxRoll` charge) → add élément-de-frappe stat × scaling → crit (Agilité, capped at 35%, *adds* damage via Agilité, does not double) → `degatsInfliges` debuff → rebound mult → resistance (unless `ignoreResistances`) → Dofus team bonus (`ctx.playerDamageBonus`, player camp only) → `multOffensif` (Intelligence, capped, all casters) → round, floor at 0.
- **Support mechanics** (Eniripsa kit, all in `combat.ts`): damage goes through `infligerDegats` → **shield (`bouclier`) absorbs before HP**; `poison`/`hot` are timed effects in `effets[]` that **tick at the start of the actor's turn** in `effetsDebutTour` (poison can kill, then transmits to the combatant `derriere` if `transmet`); heals via `soigner` (incl. `soinComplet`, `allie_tous`, `soinEquipeRatio` lifesteal-to-team); `appliquerSoutien` applies bouclier/HoT/`dissipe`/`paGain`/`bonusProchainSortPct`; per-target **cooldowns** live on `acteur.cooldowns` and are enforced inside `ciblesValides`. `allie_tous`/`soi`/`invocation` spells resolve with no target click.
- **Turn order (ALTERNATING + FROZEN, since 2026-07-24)**: the whole combat plays a FIXED sequence built once from the starting roster (`ordreDuCombat` in combat.ts — also drives the UI timeline, single source; `prochainActeur` = first alive-unplayed of that sequence): best BASE initiative opens, camps alternate, the bigger camp's surplus closes the round (4v2 → A E A E A A). Deaths just skip their slot — NO re-interleaving (A E A E → first E dies → A A E), and a resurrected combatant gets its original slot back. Consequence: mid-combat `initiative` effects are INERT for ordering (Déferlante's −init rider no longer delays anyone — flagged for a redesign; Étreinte glaciale's was replaced by a guaranteed −1 PA on every target hit, retraitPA rolled PER TARGET in zone spells since then). **Summons that play** (`invoquePar`: Kankreblath's monsters, Shin Larve's larvae) are OUTSIDE the alternation: they always act immediately after their summoner, every round, and **die with their summoner** (`purgerInvocationsOrphelines`, cascade — also kills the Poupée and breaks the Lance without its destruction shield). Boostache's resurrected are NOT summons (original pack members, normal alternation, survive the boss). **Obstacle invocations** (`estInvocation`: Poupée via `invoquerPoupee`, the Lance) never get a turn slot; the Poupée can `provoque` — enforced in `ciblesValides`. One poupée per summoner. `Vigueur des bois` sets `bonusOffensifProchain`, a one-shot % consumed by the next damage cast.
- **Secondary-stat caps are mandatory**: crit chance capped at 35% (Agilité, 5% floor for everyone), crit damage bonus capped at +45%, final damage multiplier (Intelligence) capped at +20%, esquive capped at 50%. Don't remove the `Math.min` caps. See *Archétypes & éléments* below for the full formulas — they superseded the earlier ~50%-everywhere caps described here before the 2026-08-05 rework.
- **HP persists between fights/nodes** within a run — the Taverne node is the only heal. A wipe ends the run but **must not erase `Meta.dofus`**.
- **PV model**: `pvMax = pvBase + vitalitéFinale × PV_PAR_VITA` (spec-literal). Monster damage in `data.ts` is tuned against the resulting (inflated) player HP — retune both together.

## Scope discipline

Each tranche is deliberately narrow; the spec's validation criteria define "done". Everything in the "out of scope" list above is **deferred** — resist pulling it in. Values in `data.ts`/`progression.ts` are meant to be adjusted. Crit is a multiplicative bonus (affects players AND monsters).

### Mode Ascension

Once a tranche has been cleared once, it becomes **replayable at an escalating difficulty**: 8 cumulative paliers A1→A8, catalogue in `ASCENSION` (`data.ts`), merged via `effetsAscension(palier)` in `run.ts` (booleans OR, percentages "last wins", multipliers compose, bonuses add — see `ascension.test.ts`). Effects: wider normal-fight packs (`packPlus1`, +1 zone monster, never in the donjon), reduced taverne heal (`tavernePctAscension`, 50%→30% from A2), enraged bosses (`bossEnrage`, stacking per-turn damage via `appliquerEnrage` in `combat.ts`), global enemy PV/offensive-stat multipliers, doubled elite modifiers from A5 (`appliquerModificateursElite(..., 2)`, `genererCarte` draws 2 distinct ids per combat_dur node), reduced starting/recruit HP (`pvDepartPct`), and a final-zone-only PA bonus on the last boss. Applied to enemy packs via `appliquerAscensionEnnemis` (`run.ts`), keyed by encounter `type` (`combat`/`combat_dur`/`donjon`) and `derniereZone`. **Per-tranche record** in `Meta.ascension` (`recordAscension`/`enregistrerAscension`, never decreases); the Dofus drop rate gets **+1%/palier** (`tauxDofusAscension`). Palier picked on a start-screen selector (locked above the tranche's current record + 1). Four achievements gate on it (`ascension_1/3/5/8` in `SUCCES`, run.ts). `npm run sim` measures it too via a top-of-file `ASCENSION` constant (default 0 = base game; taverne/starting-HP effects are out of the sim's scope since it only measures isolated encounters, not full runs — documented in a comment next to the constant) — A0 reproduces the reference win-rate table below; A8 degrades progressively (no early-zone brutal 0%, later zone bosses trend toward unwinnable by design).

### Multi-tranches (socle, 2026-07-27)

Une run = une tranche, mémorisée dans `RunState.trancheId` : le cap de niveau (`niveauMaxTranche(trancheId)`, i.e. `trancheDe(trancheId).niveaux[1]`), le niveau de DÉPART (`niveaux[0]` — t1 démarre à 1, t2 à 50, lu par `nouvelleRun`/`persoAuNiveau`), la liste des zones et la **toile** en découlent tous de `TRANCHES`/`trancheDe`. La numérotation des toiles est continue entre tranches (`offsetToile` — t2 commence à la toile 13), donc butin, prix d'HDV, kamas et XP par toile continuent de croître sans coefficient de tranche additionnel.

**Déverrouillage** (`trancheDeverrouillee`/`trancheJouable`, `run.ts`) : une tranche est ouverte si la précédente a été vaincue au moins une fois — `recordAscension(meta, trancheId) !== undefined` sert de preuve du clear (`Meta.ascension[id]` n'est renseigné qu'à la victoire), **aucun champ de `Meta` supplémentaire**. Piège de rétro-compat corrigé le 2026-07-28 : `Meta.ascension` n'existe que depuis le mode Ascension, donc une save ayant remporté la T1 AVANT cette fonctionnalité ne portait que `victoires` et restait bloquée devant la T2 ; `chargerMeta` crédite désormais un clear `{ t1: 0 }` à toute vieille save sans `ascension` mais avec `victoires > 0` (t1 était la seule tranche existante, l'inférence est sûre). `trancheJouable` exige en plus que la tranche ait des zones (`trancheDe(trancheId).zones.length > 0`) **et ne soit pas `enChantier`** : t3-t5 restent affichées « 🚧 En construction » et non cliquables tant qu'elles sont vides, et **t2 porte `enChantier: true` depuis le 2026-08-02** — ses trois zones existent mais leur équilibrage n'est pas fait, donc elle reste visible, déverrouillable et **mesurée par `npm run sim`** sans pouvoir être lancée. Retirer ce seul drapeau de `TRANCHES` l'ouvrira, sans autre changement. Le rack `.tranches-rack` de l'accueil (`ui/accueil.ts`) est un vrai sélecteur de tranche, pas juste un affichage.

**Héritage** : à la victoire, le recap propose d'archiver l'équipe (`archiverEquipe(meta, trancheId, run)` — instantané profond dans `Meta.heritage[trancheId]`, **équipement PORTÉ uniquement** : ni `RunState.inventaire` ni les kamas ne traversent). Au lancement d'une tranche ≠ t1, `heritagePour(meta, trancheId)` lit l'archive de la tranche PRÉCÉDENTE (`TRANCHES[idx-1]`, `null` si absente → retour accueil) et `showDepartTranche` (`ui/accueil.ts`) offre trois départs : équipe héritée avec équipement (`runDepuisHeritage(arch, true, trancheId, ascension)`), équipe héritée nue (`avecStuff = false`), ou équipe neuve composée par le joueur (`nouvelleRun(choix, ascension, trancheId)`) — les trois font naître les héros au niveau de départ de la tranche via `persoAuNiveau(classeId, niveau, position)`, qui pré-alloue les points de caractéristique cumulés (`(niveau-1) × POINTS_PAR_NIVEAU`).

**T2 a sa première zone (Clos des Blops, 2026-07-27)** : `TRANCHES[1].zones = ["clos_des_blops"]`, toile **13** (`offsetToile("t2") = 12`), niveau d'entrée 50 — T2 est donc désormais jouable (pas seulement déverrouillable) une fois T1 vaincu une fois. **15 espèces** (4 Blops, 4 Biblops, 3 variantes, 4 Blops Royaux), **8 capturables en archi** (les 4 Blops + les 4 Biblops ; variantes et Royaux n'ont pas d'archi sur Metamob — vérifié). Les Royaux ont **6 PA** (contre 10 pour un boss T1 seul, la salle en alignant deux) et leur liste réelle est `[signature, charge, morsure]` — **pas d'`ecrasement`** : à 6 PA ils lancent exactement UNE action par tour, la signature (6 PA, `cooldownTours: 2`) quand elle est prête, `charge` (6 PA) sinon ; `morsure` (4 PA) ne sort jamais avec l'IA agressive (elle joue le sort le plus cher). Ils sont montés à **80 en stat dominante** (34 auparavant) pour être sans ambiguïté la menace de leur salle : `charge` d'un Royal ≈ 89 dégâts/tour contre ≈ 64 pour un Gloutoblop, ≈ 33 pour un Blopignon et ≈ 40 pour un Blop normal. Les dégâts de poison sont **plats** (ils ne scalent pas avec les stats du monstre) : 12/tour sur toute une rangée (`vapeurs_corrosives`) est une valeur absolue à juger contre les PV des héros, à retenir pour la passe d'équilibrage. **Nelween** : boss unique, 10 PA, `[vapeurs_corrosives, charge, morsure]` — le repli `charge` n'est pas décoratif : sans lui, sa signature en recharge un tour sur deux, il gaspillerait 6 de ses 10 PA et tomberait à ~145 dégâts/tour ; avec, il tourne à ~172 contre ~142 pour son escorte Kolérat. Il compte désormais les dégâts engagés par le poison (`degats × duree`) et évalue `zoneLigne` sur un **nombre de cibles paramétrable**, dont le cas le plus défavorable au boss — **une seule cible** en rangée avant, formation légitime face à des sorts `ennemi_ligne`. **T2 a sa cinquième zone (Terrier du Wa Wabbit, 2026-08-03)** : `TRANCHES[1].zones` gagne `terrier_wa_wabbit`, toile **17**, niveau d'entrée ≈66. **10 espèces, 6 capturables en archi.** **Premier écart assumé du projet à la composition d'un donjon unique** : DofusDB connaît DEUX donjons Wabbit — le **Terrier** (id 17), peuplé de robots (Wobot, Tiwobot, Wobot Kiafin, Black Wo Wabbit, Blanc Pa Wabbit, boss Wa Wobot), et le **Château** (id 52), peuplé des lapins classiques. Le Terrier réveille `contre`, la posture de riposte, qui existait dans `combat.ts` depuis le Duel du Sram et le Sabre Shodanwa sans qu'**aucun ennemi n'ait jamais riposté** : le code est pourtant écrit sans notion de camp (`attaquant.camp !== cible.camp`) et `infligerDegats` reçoit bien attaquant + ctx dans les deux sens ; le commentaire « contre/riposteAvant sont des mécaniques côté joueur uniquement » décrivait le CONTENU de l'époque, pas une restriction du code. Trois sorts, aucune nouveauté moteur : `riposte_mecanique` (4 PA, Wobot/Tiwobot, posture 25 %/2 tours), `contre_mesure` (6 PA, cd 2, Wa Wobot, 50 %/3 tours), `caprice_royal` (6 PA, cd 2, Wa Wabbit, `zoneLigne` + `retraitPA: 2` à `retraitPAChance: 1`). ### Archétypes & éléments (2026-08-05) — fin de l'allocation manuelle

**L'allocation manuelle de points a été supprimée.** Les stats d'un héros sont désormais une
fonction PURE de sa classe et de son niveau (`statsFinales`, `src/progression.ts`) : il n'y a
plus de points à distribuer, plus de mode Libre, plus de `restat`. `Progression` est réduit à
`{ niveau, xp }`. `investirN`/`POINTS_PAR_NIVEAU` n'existent plus.

**Chaque classe porte un `archetype` (`melee` | `distance`) et deux `elements` fixes**
(`Classe.archetype`/`Classe.elements`, `types.ts`) — table complète et source de vérité dans
`CLASSES-ELEMENTS.md` à la racine (vérifié en synchro avec `src/content/classes.json` par
`src/archetypes.test.ts`). À chaque niveau, un héros gagne des points dans **chacun** de ses
deux éléments plus de la vitalité, au tarif croissant `coutPoint` (inchangé — 1/2/3 selon le
seuil déjà investi) :

| Archétype | Par élément | Vitalité |
|---|---|---|
| `melee` (Iop, Féca, Forgelance, Ouginak, Sram, Ecaflip, Sadida) | +3 dans chacun de ses 2 éléments | +2 |
| `distance` (Cra, Roublard, Eniripsa, Éliotrope, Xélor) | +4 dans chacun de ses 2 éléments | +1 |

`statPourPoints` calcule ce tarif comme une **fonction pure du niveau** (boucle sur `coutPoint`,
bornée à ~800 itérations au niveau 200 — plus d'état d'allocation à faire évoluer, juste une
conversion points→stat) — le mêlée retrouve EXACTEMENT la courbe de l'ancien système à
allocation pleine dans une seule stat (147/248/315/365 à L50/100/150/200 : 3 pts/niveau, seuils
200/300). `statElement`/`STAT_PAR_ELEMENT` (terre→force, feu→intelligence, air→agilité,
eau→chance) décident où tombent ces gains ; l'élément de frappe sélectionne laquelle des deux
stats sert au scaling de dégâts pour un coup donné — depuis le rework du 2026-08-06 ce choix
n'est PLUS stocké sur le personnage, il est recalculé à chaque coup contre chaque cible
(`elementContre`), voir *Élément de frappe* plus bas.

**Les quatre éléments ont un effet secondaire, hors tarif, hors équipement** (tous en plus des
gains de niveau ci-dessus, calculés dans `statsFinales`) :

| Élément | Effet secondaire | Formule |
|---|---|---|
| terre (force) | +vitalité passive | `Math.floor(force / 5)`, 1 point tous les 5 de force |
| feu (intelligence) | dégâts finaux | `multOffensif` : `1 + min(0.2, intelligence × 0.001)`, plafond +20% |
| air (agilité) | taux **et** dégâts de critique | `chanceCrit` : `min(0.35, 0.05 + agilité × 0.0025) + crit_plat`, plancher 5%, plafond 35% ; `bonusDegatsCrit` : `min(0.45, 0.25 + agilité × 0.002)`, plafond +45% |
| eau (chance) | +prospection passive | `Math.floor(chance / 3)`, 1 point tous les 3 de chance |

Le plancher de 5% de critique s'applique à TOUT le monde, y compris les 8 classes jouables sur
11 qui n'ont pas l'air dans leurs deux éléments (`CLASSES-ELEMENTS.md` : air ne couvre que 3
classes — sans plancher, elles ne critiqueraient jamais). `multSoin` lit désormais la
**caractéristique de frappe du lanceur** (`statElement(statsEffectives(c), elementDeFrappe(c))`),
pas l'intelligence spécifiquement — un soigneur sans feu (Sram, Ouginak…) soigne quand même à
plein régime sur sa propre stat de frappe ; ça vaut aussi pour le Dragoss Protéiforme (T2,
toile 21, seul soigneur ennemi du jeu), dont la puissance de soin lit désormais sa dominante.

### Elite nodes, recap, achievements, Armurerie

- **Elite nodes (combat_dur) get a pack-wide modifier drawn at MAP GENERATION** (`MapNode.eliteModif`, set in carte.ts `enrichir`, shown on the map node label + hover tooltip — playtest showed surprise modifiers were run-killers; catalogue `MODIFICATEURS_ELITE` in data.ts, values toned to +20%/+20%PV/+1PA, applied by `appliquerModificateurElite(_, _, modifId)` with random fallback for zaap-revealed fights and old saves; reward = donjon-rate loot; the sim applies modifiers on its elite rows).
- **End-of-run recap** (`showRecap`): per-hero damage via the engine's `onDegats` hook, MVP, counters — `RunStats` on `RunState`, serialized with the run save.
- **Achievements**: `SUCCES` catalogue + `verifierSucces` in run.ts, persisted in `Meta.succes`, checked at run end, shown in the recap and via the 🏆 button on the start screen; rewards deferred to the item system.
- **Armurerie** (item collection, mirror of the Bestiaire): `Meta.collection` maps itemId → best rarity ever obtained (old saves may still carry `"base"` entries from the removed legacy items — harmless, never displayed), recorded by `enregistrerCollection` (run.ts) at drop time (`recompenserButin` in main.ts) and on HDV purchase (`showHDV` takes `meta`); `showArmurerie` lists every zone's catalogue (toile pools normales + élite/boss badges) — never-obtained items ghosted, obtained ones solid with the halo/name-color of the best rarity; buttons on the start screen and map top bar (`/assets/menu/armurerie.png`, 🛡️ text fallback while the asset doesn't exist).
